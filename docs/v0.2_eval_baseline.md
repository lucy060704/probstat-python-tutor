# v0.2 评测基线：v0.1-mvp

## 1. 基线目的

本基线用于衡量后续 RAG、Bayesian Knowledge Tracing（BKT）和教学智能体改动是否真的
改善了独立指标，同时及时发现案例、标签或既有行为发生意外漂移。

本里程碑只冻结现状，没有：

- 修改 `evals/cases.jsonl`；
- 修改人工标签；
- 修改业务算法或题库；
- 排除失败案例；
- 改变任何已有指标的分母；
- 把多个指标合并成一个总分。

## 3. 案例指纹

案例指纹不直接对 JSONL 文件字节做哈希，因为 Windows 与 Linux 的换行符可能不同。
`normalized_case_sha256()` 使用以下步骤：

1. 每行 JSON 先解析为经过 Pydantic 验证的 `EvalCase`；
2. 案例按 `id` 排序；
3. 每个对象的字段名排序；
4. 使用无多余空白、`ensure_ascii=False` 的稳定 JSON 编码；
5. 转成 UTF-8 字节；
6. 计算 SHA-256。

因此，CRLF/LF 换行和 JSON 字段顺序不会改变指纹；案例内容变化会改变指纹。运行时间、
延迟和环境信息不进入指纹。

## 4. 案例覆盖和分布

### 4.1 按知识点

| 知识点 | 案例数 | 占比 |
| --- | ---: | ---: |
| `mean_median` | 11 | 30.56% |
| `variance_std` | 7 | 19.44% |
| `sampling_standard_error` | 9 | 25.00% |
| `confidence_interval` | 9 | 25.00% |
| 合计 | 36 | 100.00% |

分布问题：均值与中位数案例最多，方差与标准差案例最少，两者相差 4 例。当前基线不能把
四个知识点视为等量样本。

### 4.2 按主能力维度

“主能力维度”取题目 `dimension_weights` 中权重最大的维度；并列时按
`CapabilityDimension` 枚举顺序决定。每个案例只计入一个主维度。

| 主能力维度 | 案例数 | 占比 |
| --- | ---: | ---: |
| `concept` | 10 | 27.78% |
| `calculation` | 0 | 0.00% |
| `python` | 16 | 44.44% |
| `interpretation` | 10 | 27.78% |
| 合计 | 36 | 100.00% |

分布问题：Python 主维度占 44.44%，没有任何题以 calculation 为最大权重。因此，该基线
不能单独评价“以计算为主”的诊断效果。

### 4.3 按所有被观察维度

只要题目在某维度上的权重大于 0，该案例就计入该观察维度。一个案例可以同时计入多个
维度，因此下表合计大于 36。

| 被观察维度 | 涉及案例数 | 占全部案例比例 |
| --- | ---: | ---: |
| `concept` | 36 | 100.00% |
| `calculation` | 20 | 55.56% |
| `python` | 16 | 44.44% |
| `interpretation` | 20 | 55.56% |
| 多标签计数合计 | 92 | 不适用 |

这说明 calculation 并非完全缺失，而是没有作为任何案例的主维度。

### 4.4 按案例类别和错误类型

`categories` 允许多标签，所以 36 个案例产生 38 个类别计数。

| 类别 | 案例数 | 占全部案例比例 |
| --- | ---: | ---: |
| `fully_correct` | 12 | 33.33% |
| `concept_correct_code_wrong` | 3 | 8.33% |
| `code_correct_interpretation_wrong` | 3 | 8.33% |
| `calculation_correct_conclusion_wrong` | 3 | 8.33% |
| `pandas_syntax_error` | 3 | 8.33% |
| `sd_se_confusion` | 3 | 8.33% |

分布问题：

- 完全正确案例占三分之一；
- 无关回答和信息不足各只有 2 例；

- 现有规模不足以分别估计每个知识点、维度和错误类型的稳定指标。

## 5. 六项真实基线指标

以下数值来自生成 `evals/baselines/v0.1-mvp.json` 的实际全量离线运行。

| 指标 | 分子 | 分母 | 值 |
| --- | ---: | ---: | ---: |
| 确定性判题准确率 | 30 | 36 | 83.33% |
| 误区标签准确率 | 26 | 36 | 72.22% |
| 下一步建议匹配率 | 30 | 36 | 83.33% |
| 一级提示答案泄露率 | 0 | 3 | 0.00% |
| API 失败率 | 0 | 36 | 0.00% |
| 平均延迟 | 408.7067 ms 延迟总和 | 36 | 11.3530 ms |

不生成总分。每项指标必须单独解释。

### 5.1 确定性判题准确率

```text
分子 = 成功报告中，(overall_correctness == 1.0) 与 expected_correct 一致的案例数
分母 = 成功生成 DiagnosticReport 的案例数
```

当前为 `30 / 36`。`case_016` 至 `case_021` 的答案字段正确，但推理或结论错误；现有
确定性判题主要读取 `answer`，因此这 6 例与人工整体标签不一致。本轮保留这一真实结果，
没有调整算法或标签。

### 5.2 误区标签准确率

```text
分子 = 系统 misconception_tags 集合与 expected_misconception_tags 集合完全相等的案例数
分母 = 成功生成 DiagnosticReport 的案例数
```

当前为 `26 / 36`。这是严格的“整组完全相等”，不是逐标签 precision、recall 或 F1。
已知不一致包括：

- `case_016` 至 `case_021`：答案正确但推理错误，系统没有生成对应推理误区；
- `case_033` 至 `case_036`：无关或信息不足回答返回了题目通用误区，而不是人工标注的
  `irrelevant_response` 或 `insufficient_evidence`。

### 5.3 下一步建议匹配率

```text
分子 = _classify_action(report) 与 expected_action 相等的案例数
分母 = 成功生成 DiagnosticReport 的案例数
```

当前为 `30 / 36`。同样受 `case_016` 至 `case_021` 的答案与推理冲突影响：系统把答案
字段判为正确并推荐下一题，人工标签要求继续引导。

### 5.4 一级提示答案泄露率

```text
分子 = feedback 或 recommended_action 命中该案例 forbidden_hint_tokens 的一级提示案例数
分母 = 成功生成报告且 hint_level == 1 的案例数
```

当前为 `0 / 3`。该结果只说明 3 个指定案例中的报告文本没有命中禁止 token。它不代表
所有提示都绝不泄露，也没有检查 Streamlit 页面由 `LearningService.get_hint()` 返回的
实际 UI 提示。

### 5.5 API 失败率

```text
分子 = 评测流程未生成 DiagnosticReport 的案例数
分母 = 全部评测案例数
```

当前为 `0 / 36`。

**metric_scope：当前基线运行于离线模式，该指标实际表示评测流程未生成报告的比例，
不代表真实 OpenAI API 的在线可靠性。** 保留 `api_failure_rate` 名称只是为了兼容现有
代码和历史输出。

### 5.6 平均延迟

```text
分子 = 全部案例的 latency_ms 之和
分母 = 全部案例数
value = 分子 / 分母
```

冻结文件记录 `408.7067 / 36 = 11.3530 ms`。生成前一次运行得到 11.60 ms，第一次
`--check-baseline` 复跑得到 10.94 ms，说明同一机器上也会自然波动。

平均延迟只要求：

- 字段存在；
- 是有限、非负数值；
- 分子、分母和值内部一致。

它不参与跨运行精确相等的基线检查。

## 6. 基线检查规则

运行：

```powershell
.\.venv\Scripts\python.exe evals\run_evals.py `
  --check-baseline evals\baselines\v0.1-mvp.json
```

严格比较：

- 规范化案例 SHA-256；
- 案例数量；
- 知识点、主维度、观察维度和类别分布；
- 五项比例指标的 numerator、denominator、value 和 metric_scope。

不精确比较：

- 平均延迟数值；
- 生成时间；
- Python/操作系统描述。

发现漂移时，脚本会分别输出：

- `案例指纹漂移`；
- `案例数量漂移`；
- `案例分布漂移`；
- `确定性指标漂移（具体指标名）`。

脚本不会只返回笼统的 `baseline mismatch`。

## 9. 已知问题和局限

### 9.1 数据覆盖

- 只有 36 个案例和 12 道题；
- 知识点分布不完全均衡；
- Python 主维度偏多，没有 calculation 主维度案例；
- 提示泄露只有 3 个一级提示案例；
- 无关回答和信息不足案例各只有 2 个；
- 案例与算法在同一仓库中共同开发，尚无独立盲测集。

### 9.2 指标设计

- 前三项指标以成功报告为分母；若未来出现失败，需要同时查看 API 失败率；
- 误区标签只做严格集合相等，没有逐标签 precision、recall 和 F1；
- 提示泄露只做禁止 token 匹配，无法识别所有语义改写；
- 提示泄露没有覆盖实际 UI 提示；
- 平均延迟是本地离线墙钟时间，不代表在线模型延迟；
- API 失败率不是在线 OpenAI API 可靠性；
- 当前没有 token 和成本指标；
- 没有模糊总分，也不应在后续添加。

### 9.3 当前系统能力边界

- 判题主要依赖 `answer`，不能可靠处理“答案正确但推理错误”；
- 错误答案通常得到题目预设的全部误区候选，未按回答证据细分；
- 当前 mastery 是启发式模型，不是教育测量结论；
- 当前没有 RAG、BKT 或真实在线模型评测；
- 尚未进行真实学习者实验，不能声称已经改善学习成绩。

这些问题只记录在本文件中。本里程碑没有修改案例、标签、题库或业务算法。

## 10. 后续使用原则

- v0.2 每项改动先与本基线逐项比较；
- 新案例进入开发集、验证集或盲测集前必须记录来源和标注过程；
- 不根据盲测结果反复修改规则；
- RAG、BKT 和在线智能体指标分别报告；
- 指标改善必须同时检查失败案例、延迟、成本、隐私和答案泄露；
- 本基线只能证明当前工程行为可重复，不能证明教学效果已经得到科学验证。
